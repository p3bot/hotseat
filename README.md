# hotseat

One process hosts named conversations. Callers publish into a transcript and block until a matching message exists or a deadline passes.

```bash
hotseat bus start
hotseat bus start --store /var/lib/hotseat
hotseat bus start --store /var/lib/hotseat --listen 127.0.0.1:4727 --max-body 524288
hotseat bus start --store /var/lib/hotseat --listen 192.0.2.10:4727 --token-file /run/hotseat/token
hotseat bus status
hotseat bus stop
```

`hotseat bus start` runs the bus detached from the terminal and returns after the listener is bound, the database is open, and the page is listening. It prints the pid, the listen address, the store path, and `page` as a URL. The page listens on `127.0.0.1` at the next port and calls this bus. It does not open the database. The default bus prints `page` as `http://127.0.0.1:4728`. A second bus does not start while its page port is in use. Closing the terminal does not stop the bus. The log is `hotseat.log` in the store directory. `hotseat bus status` asks a listen address whether the bus can serve. The default address is `127.0.0.1:4727`. It prints `health` as `pass`, `fail`, or `connection_failure`, and the address it contacted. When a `bus serve` process on this machine is bound to that address, it also prints that pid and the store directory that process holds. `pass` exits 0. `fail` and `connection_failure` exit 1. `hotseat bus stop` with no `--store` sends SIGTERM to the bus for the default store and to any other local `bus serve` bound to `127.0.0.1:4727`. It returns after those processes have exited and each `hotseat.db.lock` is released. A second stop, when those buses are already stopped, succeeds. A process that is not `bus serve` and holds `127.0.0.1:4727` is left running, and stop exits 1. `hotseat bus stop --store` signals only the bus for that directory.

`--store` selects the directory for `start` and for `stop`. Without `--store`, `stop` uses the default directory and also stops any other local `bus serve` on the default listen address. `status` does not take `--store`. It takes `--address`, and the default is `127.0.0.1:4727`. When `--store` is omitted the directory is `$XDG_DATA_HOME/hotseat`. An unset, empty, or relative `$XDG_DATA_HOME` uses `$HOME/.local/share/hotseat`. A relative home directory is refused and nothing is created. The database is `hotseat.db` in that directory. A database this binary will not serve, from another schema version or an earlier shape of version 1, is refused, the bus does not start, and the file is left unchanged. There is no migration. Delete `hotseat.db`, `hotseat.db-wal`, and `hotseat.db-shm` before starting the new build. This process is the only writer, and it holds `hotseat.db.lock` beside the database until it exits. The default listen address is `127.0.0.1:4727`. A loopback address accepts every operation with no token. A hostname is resolved once and the process listens on one address from that lookup: a loopback address when every answer is loopback, otherwise a non-loopback address. Any other address requires `--token-file` and does not listen when the file is missing or empty, and no database is created. A failed bind creates no database. The file holds one shared token. A trailing newline is ignored. The token is printable ASCII with no spaces. The process does not log it. Passing the file on loopback does not turn the check on. `GET /health` is unauthenticated on every address. The body is `pass` or `fail`. The default maximum body is 512 KiB. One bus runs for each store directory. A second start prints the running process and does not change it.

## Protocol

Every operation is `POST` of one JSON object to `/<operation>`. A completed call responds `200` with one JSON object. Read `outcome`. It is `ok`, `timeout`, `refused`, or `unavailable`. A dropped connection has no body and is not a timeout. Unknown JSON fields are ignored.

A loopback listener ignores credentials. Any other listener requires the token on every operation, including from a peer on the same machine. The header is `Authorization: Bearer` and the token. `WriteToken` in package bus is that header. A missing token is refused with `token is required`. A wrong token is refused with `token does not match`. Nothing is written. The token does not select `from` and is not stored.

`GET /health` is not an operation. It takes no token on any address. The body is `pass` and status 200 when the bus can read the schema it serves, and `fail` and status 503 otherwise. A trailing newline is the only other byte. The body does not carry the pid, the listen address, the store path, or the token.

| Call | Body |
| --- | --- |
| `/create` | `{"name","task"?,"ticket"?,"seat"?,"directory"?,"prompts"?,"custom"?,"roster"?}` |
| `/publish` | `{"conversation","from","to","body","txid","kind","re"?}` |
| `/read` | `{"conversation","cursor","limit","name"?,"kinds"?}` |
| `/wait` | `{"conversation","cursor","name"?,"deadline"?,"kinds"?}` |
| `/close` | `{"conversation"}` |
| `/list` | `{}` |
| `/messages` | `{"limit","before"?}` |
| `/watch` | `{"cursor"?,"conversation"?,"rev"?,"limit"?,"deadline"?}` |
| `/register` | `{"conversation","name"}` |
| `/member` | `{"conversation","name","status"?,"pid"?}` |
| `/session` | `{"conversation","name"?,"session"?}` |
| `/members` | `{"conversation"}` |
| `/record` | `{"conversation","record",...}` |
| `/records` | `{"conversation"}` |

`to` is an array. `[]` is empty. `["all"]` is the single value all. Any other array is an ordered name list and is not sorted or deduplicated. A different order is different content. `kind` uses the same character rules as a name. The bus stores that name and does not check its meaning, so `act` and any other legal name are stored. `kinds`, when present, is an array of those names. Omit it and read and wait match as they do without a kind filter. An empty array is refused. `re` is the `seq` of an earlier message of the same conversation that this publish responds to. Omit it, or send `null`, to respond to nothing. A value that is not an integer greater than zero, including a string or a fraction, is refused. A `seq` of another conversation, a `seq` that does not exist, and the publish's own `seq` are refused and write nothing. Every message object from publish, read, wait, watch, and `/messages` has `re`, the integer or `null`. `deadline` is a Go duration such as `30s` or `500ms`, or an RFC3339 end time. Omit it to wait until a match or a dropped connection. A duration is measured from arrival. An end time is absolute on the bus clock. A time already past times out at once when nothing matches, and a retry sends that same time.

An ok `/messages` returns the newest `limit` messages across every conversation, highest `seq` first. Each message includes `conversation`. With `before`, only messages whose `seq` is less than `before` are returned, so the lowest `seq` of one result is the next `before`. A `before` less than 1 is refused. There is no command for this route.

`/watch` takes `cursor`, `conversation`, `rev`, `limit`, and `deadline`, each optional. `limit` is required with `cursor` and follows the read range rule. `conversation` uses the name grammar. A name with no conversation matches no message and is not refused. `deadline` follows `/wait`. An ok watch returns `messages` with `seq` greater than `cursor`, oldest first, in that conversation or every conversation, at most `limit`, each with `conversation`. It also returns `more`, true when further matching messages follow the last one returned, and `rev`. Omit `cursor` and the watch returns no messages and waits on `rev` alone. It returns at once when a matching message exists, when `rev` is omitted, or when `rev` differs from the current counter. Otherwise it blocks until one of those holds, the deadline passes (`timeout`), the connection drops, or the bus stops. `rev` is a change counter for the conversation list, kept in bus memory. It starts at a random value below 2^53 when the bus starts, so a restarted bus does not return a value a caller still holds. Compare it for equality only. It increases on a create that inserted, on a close that changed the status, and on a stored publish to a conversation other than the one holding the newest message. An idempotent publish and a close of a closed conversation change nothing and wake no watch. Omit `rev` on the first watch. There is no command for this route.

`seq` is assigned at commit. It increases across the whole store and within each conversation, with gaps, so one conversation's messages need not be numbered 1, 2, 3. A cursor is a `seq` the caller has seen. `cursor` `0` means the caller has seen no message. The bus does not store cursors or transaction ids except the txid recorded on an accepted message. The caller passes both on each call.

An ok create returns the conversation, including its binding. Omitted binding fields are stored empty. JSON always includes the keys: empty text is `""` and an empty list is `[]`. `prompts` and `roster` keep the caller's order. A roster name uses the name grammar. A duplicate roster name is refused. A roster requires a `seat` that is one of those names. A seat with an empty roster is refused. Empty roster and empty seat is a name-only create. An empty string inside `prompts` is refused. A name that already exists returns that conversation, its stored binding, and `"already_existed": true`, and writes nothing. Create does not insert member rows.

An ok publish returns the message, including `seq` and `kind`, and `conversation` with its binding, only after it is durable. `kind` is required. An attempt is the conversation, the sender, and `txid`. The bus requires that id and does not generate one. The same attempt with the same `kind`, the same `to`, the same body, and the same `re` returns that message and `"already_stored": true`, including after close, and writes nothing. The same attempt with a different `kind`, `to`, body, or `re` is refused and writes nothing. A `re` present on one and absent on the other is different. Another sender with that `txid` stores a new message. Close sets `status` to `closed` and still accepts a new message. That publish returns `status` `closed`. Publish, read, wait, and the member routes follow the same rules on a closed conversation.

An ok named read returns messages addressed to that name. `kinds` keeps only listed kinds. An ok unnamed read with `kinds` returns only listed kinds. The limit counts returned messages. An ok named wait returns every message after the cursor through the first addressed message of a listed kind, and `match_seq`. Omit `kinds` and the match is address alone. Messages of other kinds, and messages addressed to other names, stay in that span. An ok unnamed wait returns only the next message, or, when `kinds` is set, the next message of a listed kind. Timeout returns no messages. Close does not end a wait.

`/register` sets the registered time from the bus clock. The status becomes `registered` only when the row is `launched`. `running`, `exited`, `timed-out`, and `registered` keep their status. The name must be a roster name that already has a row. `/member` with `status` `launched` inserts that row. A second `launched` is refused. `running`, `exited`, and `timed-out` update an existing row. `pid`, when sent, is an integer greater than zero and is stored only with a status. A pid without a status is refused and writes nothing. `/member` with no `status` and no `pid` returns that row, including `pid`, and does not return a session id. `/members` returns name, launched time, registered time, and status, in roster order, with no session id and no pid. `/session` stores or returns session ids for the caller of that route. There is no command for it. Session ids and pids are absent from read, wait, list, and `/members`.

`/record` and `/records` hold `hotseat run`'s decision records, insert-only facts about messages that `run` reads back on a continuation. There is no command for either route. Records are absent from read, wait, watch, list, member list, and the page, and neither route changes `rev` or wakes a wait or watch. The bus log holds each call and its outcome and no record content. `record` selects the write, and each seq is an integer greater than zero:

| `record` | Fields | Key |
| --- | --- | --- |
| `set` | `turn`, `findings` (may be `[]`) | turn |
| `grouping` | `turn`, `drops` (`[{"finding","kept"}]`, may be `[]`) | turn |
| `settle` | `finding`, `proposal`, `proposal_kind` | finding |
| `fix` | `finding`, `fixed` | finding |
| `halt` | `finding` | conversation |

`turn` is a `turn` message, each finding a `finding`, `proposal` the finding itself (`proposal_kind` `finding`) or a later `propose` or `dismiss`, and `fixed` a `fixed` message after the settle. A set with exactly one finding also writes its grouping with no drops and returns it beside the set. An ok record returns the stored record in the shape `/records` uses, and `already_stored`. `after` is the conversation's highest `seq` when the record commits. The bus assigns it and ignores an `after` the caller sends. A fix has `settled_after`, its settle's `after`, instead. A write that matches the stored record on its key, ignoring `after`, returns that record and `"already_stored": true` and writes nothing, so a retry after another message was published still matches. Findings and drops compare as sets. A write that differs on the same key is refused with `transaction id reused with different content`. A repeated seq in `findings`, and a repeated `finding` in `drops`, are refused. A missing message or record, a message of the wrong kind, a finding already in another set, a drop that keeps itself or names another set, a `proposal_kind` that differs from the stored message, and a `fixed` used by another fix are one reason, `record breaks a reference, kind, or uniqueness rule`. Three rules have their own reasons: a kept finding is not itself dropped, a settle or a halt names a kept finding of a set that has a grouping, and a fix belongs to a settle whose proposal is not a `dismiss`. An ok `/records` returns `sets`, `groupings`, `settles`, `fixes`, and `halts`, each in key order, and an empty list is `[]`.

`refused` names the broken rule in `reason` and writes nothing. `unavailable` means the change could not be made durable and writes nothing.

```bash
curl -s localhost:4727/create -d '{"name":"job"}'
curl -s localhost:4727/publish -d '{"conversation":"job","from":"alice","to":["bob"],"body":"hello","txid":"1","kind":"say"}'
curl -s localhost:4727/wait -d '{"conversation":"job","cursor":0,"name":"bob","deadline":"30s"}'
```

## Client

The same binary calls a bus that is already running, then exits. The default address is `127.0.0.1:4727`. `--address` aims one invocation at another bus. `--token-file` reads the token for a non-loopback bus. The token is not a command-line argument. Omit the flag for loopback. The caller passes the cursor. Omit `--txid` and publish writes `txid: ` and 10 lowercase hex characters to stderr, then sends that id. Pass `--txid` to send that value, including an empty one. The line is written before the call and flushed. A dropped call is retried once with that same id. The client does not store the id.

```bash
hotseat create --name job
hotseat publish --conversation job --from alice --kind say --to bob --body hello
hotseat publish --conversation job --from alice --kind say --to bob --body hello --txid 1
hotseat publish --address 192.0.2.10:4727 --token-file /run/hotseat/token --conversation job --from alice --kind say --to bob --body hello --txid 1
hotseat publish --conversation job --from alice --kind say --to bob --body-file - --txid 1
hotseat publish --conversation job --from bob --kind say --to alice --body yes --re 1
hotseat read --conversation job --cursor 0 --limit 50
hotseat read --conversation job --cursor 0 --limit 50 --kind say --kind turn
hotseat wait --conversation job --cursor 0 --name bob --deadline 30s
hotseat close --conversation job
hotseat list
hotseat member register --conversation job --name alpha
hotseat member list --conversation job
```

`--kind` is required on publish. `--re <seq>` sends `re`. Omit it and the field is left out. A message with `re` prints `re: <seq>` after the `kind` line, on publish, read, wait, and attend. A message without it prints no `re` line. Repeat `--kind` on read or wait to send `kinds`. Omit it and the field is left out. `--body` is the message. `--body-file` reads it from a file, and `--body-file -` reads stdin, so a body can be larger than one command argument. Pass exactly one of the two. A body or a transaction id that is not valid UTF-8 is `refused` with that bus rule, and the client does not connect. `hotseat create` sends a name only. `hotseat list` and the create result print the binding, omitting empty fields, in roster order. The list puts the conversation with the newest message first, by that message's `seq`. Conversations with no message follow, ordered by name. `hotseat member list` prints name, launched time, registered time, and status. It does not print a pid or a session id.

Each command prints one text result and exits. `outcome` is `ok`, `timeout`, `refused`, `unavailable`, or `connection_failure`. A field on one line is `name: value`. A message body is always a byte count and then those bytes, and so is any other value that contains a newline. The count keeps an empty body, more than one line, and a line that looks like a field inside the value. A usage error is a message on stderr and no stdout. A dropped call is retried once with the same arguments. Timeout is only the bus outcome. A full read page carries each message `seq`. The client does not request the next page.

```text
outcome: ok
already_stored: false
conversation:
name: job
status: open
message:
seq: 1
time: 2026-10-08T07:00:00Z
from: alice
kind: say
to: bob
txid: 1
body <<5
hello
```

## Run

`hotseat run` drives one conversation on a bus that is already listening. It does not start the bus and it does not open the database. It publishes the task as `owner`, launches each roster member through `start`, and exits when the acting seat posts `done` or a safety rail trips. After a stopping `done`, `run` closes the conversation, starts no further launch, and stops every other running member at once. The sender of that `done` gets up to 30 seconds to exit before it is killed, so `run` can exit up to 30 seconds after the `done`. A sender that exits zero in that period is `exited` with its session id stored. A sender that exits non-zero, reaches the process limit, or prints no session id in that period is `timed-out` and publishes `error`, and nobody is handed the seat. A sender killed at the end of the period is `timed-out` and publishes no `error`. The bare name is the ticket id, a hyphen, and the task slug. With no ticket the slug is the whole name. A taken bare name gains one 4-character code. A second run of the same task creates a new conversation unless `--conversation` names the existing one.

A `turn` launches each roster member in its `to` that has not timed out, unless that member has already answered it. Once that member's earlier process has ended, `run` reads the transcript. A member that has published a `say` or `finding` after the `turn` whose `re` names that `turn` has answered and is not launched for it, whatever its `to`. A `say` or `finding` whose `re` names another message has not answered. One with no `re` has answered when it names the turn's sender in `to`, and `all` in `to` does not count. An `ask` does not answer. A live run, `--conversation`, and the `no reply` report follow the same rule. Each turn prompt gives `--re` with the turn's `seq` in the publish command for the `say` and for each `finding`. A `turn` whose body `run` rejects, and each name outside the roster in a turn's `to`, is reported with `error` class `bad turn`. A rejected `turn` counts toward `--max-turns` when a live run reads it, and not when a continuation reads it stored.

The roster is `--agents` or `HOTSEAT_AGENTS`, a space-separated list of `name=module:model`. There is no `HOTSEAT_MEMBERS`. The flag wins over the matching `HOTSEAT_*` variable. `--seat` or `HOTSEAT_SEAT` names the seat. When both are absent, the seat is the first roster name in ASCII byte order. `--prompts` or `HOTSEAT_PROMPTS` and `--instructions` or `HOTSEAT_INSTRUCTIONS` are stored on the conversation. `--ticket` or `HOTSEAT_TICKET` selects the code-root the members launch in. Without a ticket, they launch in the directory `run` was started in.

`--max-turns` or `HOTSEAT_MAX_TURNS` defaults to 500 `turn` messages. `--timeout` or `HOTSEAT_TIMEOUT` limits one member process. The default is 8 hours. It is not a limit on the conversation. `--interactive` or a non-empty `HOTSEAT_INTERACTIVE` disables that process limit and keeps the turn cap. `--permission` or `HOTSEAT_PERMISSION` defaults to `auto`. `--max-launches` or `HOTSEAT_MAX_LAUNCHES` defaults to 300 member processes in one `run` process. It counts every launch kind, applies to every task, starts from zero on a continuation, and stays on with `--interactive`. `--address` and `--token-file` follow the other client commands. A non-default address or a token path is passed only in the member launch prompt. The token value is not printed.

A task's `min_members`, read with `start get --field min_members`, is the smallest roster `run` accepts. A task that omits it has a minimum of 1. A smaller roster exits with an error and creates nothing. `--conversation` applies the same check to the stored task and roster, after it reports a stored stopping `done`, so a replay gives the same result after the minimum rises. That refusal leaves a member process still running from an earlier run alone, and the next continuation watches it. A live member is one that is not `timed-out`. When a member times out and fewer than `min_members` are live, or a continuation that can launch finds that already true, `run` publishes `error` to `owner` with class `below minimum`. When a launch would pass the cap, it publishes `error` with class `launch cap`, once. In both cases `run` starts no further launch, including a handoff. Running members finish and keep their session ids. A `turn` stored meanwhile is not acted on. `run` then exits non-zero with `outcome: error` and the conversation open, once the last running member exits. A stopping `done` in that period still closes the conversation as any `done` does. A member `run` stops itself on a `done` or a `--max-turns` stop is not a failure. A timed-out member does not come back, so the owner starts a new run. `--conversation` can continue a launch-cap stop with a higher cap.

A member publishes each issue it finds as a `finding` during a `turn` set. A `finding` whose `re` names a set's `turn` opens a discussion in that set when its sender is a recipient of that `turn`, the set has not finished, and it was not stored after another set's `discuss` while that set's discussions are still open. A set has finished for a `finding` stored after its `discuss`, or, with no `discuss`, after the follow-up target's next `turn` or `done`. A `finding` with no `re` opens a discussion in the first set that takes it under that rule. Any other `finding`, including one whose `re` names another message or a finished set's `turn`, is reported once with `error` class `bad finding` and opens nothing. When every recipient of a set has exited or is `timed-out`, `run` publishes `discuss` from `run` with an empty `to` and the turn's `seq` as its body, including for a set with no findings. Before it, each recipient that is not `timed-out` and has not answered the `turn` is reported with `error` class `no reply` about the turn. A set with two or more findings is then aggregated. `run` launches the acting seat once to publish one `aggregate` to every roster name. Its body has one line per issue: the finding to keep, then the `seq` of each duplicate it drops, separated by spaces. Every finding of the set is on exactly one line. `run` then publishes `issues` from `run` with an empty `to`: the turn's `seq`, then one line per issue in kept-finding order, each duplicate list sorted. When the seat publishes no `aggregate`, more than one, or one that breaks that rule, `run` reports `no aggregate` or `bad aggregate` and each finding is its own issue in `issues`. A set with fewer than two findings has no aggregate launch and no `issues`. A dropped finding is not discussed, fixed, or unresolved. `run` runs the set's discussions of kept findings one at a time, in `seq` order, and only then launches the follow-up. A discussion prompt names the dropped duplicates as `duplicates:`. The follow-up prompt carries `fixed: <n>`, the number of `fixed` messages since the set's turn, then `no reply:`, `dropped:`, and `timed-out:`. A `turn` published during a set, a discussion, or a fix is queued and acted on after the follow-up.

Each discussion has one current proposal. It starts as the finding, with the finder as proposer. `propose`, `dismiss`, `agree`, `object`, and `stand` are stances. A discussion launch publishes exactly one stance, addressed to every roster name. `propose` and `dismiss` replace the proposal, make the sender the proposer, and clear every `agree`. The proposer may publish `propose`, `dismiss`, or `stand`, and `stand` only while an `object` is open. `stand` keeps the proposal and its agreements. A proposer that becomes `timed-out` counts as a `stand`. A finding settles when every roster member that is not `timed-out`, other than the proposer, has published `agree` since the proposal was set. `run` then publishes `settled`, whose body is the finding's `seq`, a space, and the agreed proposal's `seq`. A sole live member's finding settles at once. Findings and stances are read with an unnamed `hotseat read` filtered by kind, so their `to` hides nothing. Every other kind keeps its addressing. That read starts at the finding, so discussion and stall prompts also name `start`, the seq the discussion began after: the set's `issues` or else its `discuss`, or the `settled` or `fixed` of the finding before it, and on a restart past every message the continuation treats as history. A stance at or before `start` does not belong to that discussion.

The first speaker is the first live member after the finder in roster order. After a launch with one stance and one `pass` to one eligible member, that member speaks next. Otherwise the next speaker is the first member after the last speaker who has not agreed, has published no stance since the proposal was set, the proposer's last `stand`, or the proposer's timeout, and has budget left, and then the proposer while an objection is open. `--max-says` or `HOTSEAT_MAX_SAYS` defaults to 4 discussion launches for each member on each finding. The flag wins, and a value below 1 is refused. A `pass` counts toward `--max-turns`. It is not a `turn`.

When nobody can speak and the finding has not settled, the discussion stalls and `run` launches the acting seat once. It publishes `extend`, with `to` naming the members whose budget is refreshed, or `deadlock` to every roster name and `owner`. Each `extend` counts toward `--max-turns`, including one that refreshes nobody. A name outside the roster or `timed-out` is reported with `error`, and an `extend` with an empty `to` is reported against the seat. A `deadlock` stops the run at once. `run` publishes `halted` with the finding's `seq`, opens no further discussion, launches no fix and no follow-up, and launches the acting seat once more to post `done` to `owner` with `outcome: hold` and a report. Its prompt lists the dropped duplicates. There is no majority vote. When a `finding` or `propose` settles, `run` launches the finder, the sender of the `finding`, to apply it and publish `fixed` to every roster name. A fix launch with no `fixed` hands the fix to the acting seat once. A settled `dismiss` is not fixed. A seat timeout while a set's discussions run launches no handoff until they finish. Until then the backup rule picks who decides a stall or applies a fix.

Every prompt that asks for a threaded kind gives the exact `--re` in its publish command: a stance and a `pass` name the finding under discussion, an `extend` or `deadlock` the stalled finding, an `aggregate` the set's `turn`, and a `fixed` the finding whose settled change it applies. A `turn`, a `done`, and the instructions take no `re`. A missing `re` is judged by the rules above and is never an error. A present `re` that is not the message `run` expects rejects the message under its kind's class, `bad stance`, `bad pass`, `bad extend`, `bad deadlock`, or `bad aggregate`, and it still counts toward `no stance`, `extra stance`, the one `aggregate`, and the stall's one decision. An `extend` with a wrong `re` refreshes nobody, counts toward `--max-turns`, and the discussion continues. A `deadlock` with a wrong `re` publishes no `halted`, and the stall stops with `no decision`. A `fixed` whose `re` names another message does not count and is not reported, so the fix is handed off or stops with `no fix`, and it does not resolve the finding at the stop.

The stop result comes from the transcript, from the messages stored before the stopping `done`, every time a `done` stops the run, including on a `--conversation` replay. A finding is unresolved when it has no `settled`, or when it settled on a `finding` or `propose` and has no `fixed` after that `settled`. With none, `run` prints `outcome: done` and exits zero, whatever the `done` body says. Otherwise it closes the conversation, prints `unsettled: <seq>` for each finding with no `settled` and `unfixed: <seq>` for each change not applied, and exits non-zero. The final line is `outcome: deadlock` when a `halted` exists, and `outcome: unsettled` otherwise. An unsettled stop also publishes one `error` to `owner` with class `unsettled` and `re` naming the stopping `done`. A replay meets it again and does not repeat it. `hotseat attend` may exit on the `done` before it prints that `error`, so the exit status and the status lines of `run` are the reliable signal. `run` cannot undo anything the seat did before its `done`, such as `tk mark todo`. After a deadlock, the owner resolves the disagreement and starts a new run. Fixes already applied stay, and the report's undiscussed findings can be passed to the new run as a prompt.

A protocol `error` goes from `run` to `owner`. Its body is the member and the class on two lines, or the class alone. When one stored message caused it, its `re` is that message's `seq`. `bad finding`, `no reply`, `bad turn`, and `unsettled` take a transaction id derived from their fact: `bad finding/<member>/<finding>`, `no reply/<member>/<turn>`, `bad turn/<turn>` for a rejected turn, `bad turn/<member>/<turn>` for a name outside the roster, and `unsettled/<stopping done>`. A continuation that meets the same fact again gets the stored error back, stores no second copy, and prints no second status group. Every other error has a random transaction id. A caller that publishes as `run` under one of those ids with other content makes that publish a refusal, and `run` stops as on any refused publish. The protocol classes are `no reply`, `no aggregate`, `bad aggregate`, `bad finding`, `no stance`, `extra stance`, `bad stance`, `bad pass`, `bad extend`, `bad deadlock`, `no decision`, `no fix`, `no report`, and `unsettled`, which is the class alone. A discussion speaker whose launch ends `timed-out` already has its failure published, so it gets no `no stance` or `extra stance`, its `pass` is ignored, and a single stance it stored is still judged. A rejected stance, `aggregate`, `pass`, `extend`, or `deadlock` changes nothing. A seat whose aggregate launch ends `timed-out` with no `aggregate` gets no `no aggregate`. A seat whose stall launch ends `timed-out` without exactly one of `extend` and `deadlock` gets no `no decision`, and the backup rule picks who decides the stall. A live seat's stall launch that publishes neither or both, a fix the acting seat also leaves without `fixed`, and a report launch with no `done` exit non-zero with `outcome: error` and the conversation open. `--conversation` continues it.

`--conversation` does not replay stances. A set with a `discuss` takes its findings from the transcript. A set with a `discuss`, two or more findings, no `issues`, and no `settled` finding gets its aggregate launch again. A finding with `settled` is closed, and a settled change with no `fixed` gets its fix launch again. A `halted` with no `done` after it gets the report launch again and nothing else. Otherwise the first finding with no `settled` starts over with fresh budgets, and its prompts say that it restarted. The follow-up runs unless the follow-up target posted a `turn` or `done` after the set's discussions ended. A set with no `discuss` finishes as a live set does, unless every recipient has exited or is `timed-out`, the follow-up target has a later `turn` or `done`, and no recipient published a `finding` before it. A continuation starts no discussion, stall, fix, or report launch until each process left from the earlier run has exited, and a stance that process published does not count. A message stored before the continuation started, or published by a leftover process, is not judged again. A stray stance, `aggregate`, `pass`, `extend`, or `deadlock` from a launch the continuation started is reported, including while it waits for a leftover. A resume with no roster opens no discussion and publishes no marker. A stored `bad finding`, `no reply`, `bad turn`, or `unsettled` is not reported again.

Stdout is `key: value`, the same text result as the other client commands. The lines name the conversation, each status `run` writes (`launched`, `running`, `exited`, `timed-out`), each executed `turn` with its mode and its `to`, each process exit, each `issue` with each `dropped` duplicate, each opened `finding` with `from`, each accepted `stance` with `from` and `seq`, each `pass` with `from`, each `settled`, `stall`, `extend` with each refreshed name as `to` when it refreshed one, `deadlock` with `from`, `fixed` with `from`, each protocol `error` with `from` when its body names a member and `seq` when its `re` names a message, the `unsettled` and `unfixed` findings at the stop, and a final `outcome`. Registration is on `hotseat member list`. `outcome` is `done`, `deadlock`, `unsettled`, or `error`. It is `done` only when this command exits zero, which is when the acting seat posted `done`, the close succeeded, and no finding is unresolved. A session id, a pid, and the token are not on those lines. agy (Antigravity CLI) has no hotseat module, so it is not a roster module. Pass the task query when creating. When `--conversation` names a conversation that is not on the bus, the task argument is required. A resume launches a member only when `--agents` or `HOTSEAT_AGENTS` is passed again. Without that roster, the resume continues and does not launch.

```bash
hotseat run review/ticket --agents "alpha=hotseat/grok:model bravo=hotseat/claude:model" --ticket foo-x234
hotseat run --conversation foo-x234-review-ticket --agents "alpha=hotseat/grok:model bravo=hotseat/claude:model"
```

## Attend

`hotseat attend` waits as `owner` on one conversation and prints `ask`, `error`, and `done`. It calls a bus that is already running. It does not open the database, launch a process, publish, or write a member row. It does not resume a chief. A `say`, a register, and any other join are not printed. Joins are `hotseat member list`.

`--conversation` or `HOTSEAT_CONVERSATION` names the conversation. The flag wins. `--cursor` is the last finished sequence. The default is `0`, which reads from the start. The cursor stays in this process. The next wait uses the match sequence just printed. A new process reads from sequence 0 unless `--cursor` is set. `--address` and `HOTSEAT_ADDRESS` default to `127.0.0.1:4727`. `--token-file` and `HOTSEAT_TOKEN_FILE` follow `hotseat run`. The flag wins. The token value is not printed.

Each printed match is one text result: the conversation name, `match_seq`, and the message (`from`, `kind`, `re` when it has one, `to` in stored order, and the body). The bus span may contain other kinds. A `say` earlier in that span is not printed. An `ask` or an `error` is printed and attend waits again. There is no deadline. A `done` addressed to `owner` is printed and attend exits zero, including a `done` from a name other than the acting seat. A `done` that is not addressed to `owner` does not end attend. A connection failure, a refusal, or an unexpected outcome exits non-zero. The text result stays on stdout. A usage error prints no stdout.

```bash
hotseat attend --conversation job
hotseat attend --conversation job --cursor 4
```

## Web

`hotseat bus start` serves the page on `127.0.0.1` at the next port. The default is `http://127.0.0.1:4728`. `hotseat web` serves that same page for a bus that is already running, on a listen address you choose. It calls the bus. It does not open the database. The default bus address is `127.0.0.1:4727`. The default page address is `127.0.0.1:4728`, which is the page `hotseat bus start` already serves. A further page passes another loopback `--listen`. The page listens on loopback. Any other listen address is refused. The page answers for the address it listens on. On loopback, localhost with that port is the same address. `--token-file` reads the token for a non-loopback bus. The page does not receive the token. Omit the flag for loopback. The top bar searches every conversation by name, task, and ticket, in the list order. Messages, at `/`, shows the newest 50 messages across every conversation, newest first. A conversation can appear more than once. Reaching the bottom of that group loads the next older 50. Conversations, at `/conversations`, shows an Open section and then a Closed section. Each keeps that order and shows the task, ticket, and seat. An empty section stays on the page. A conversation named `.` or `..` is shown without a link. Opening `/conversations/{name}` shows its name, status, task, ticket, seat, and directory, then the newest 50 messages, latest first. Reaching the bottom of that group loads the next older 50. Loaded groups stay on the page. The page does not ask for a cursor or a limit. Send posts to `/conversations/{name}/messages`. The person at the page supplies `from`, `to`, `kind`, and the body. The transcript shows that `kind`. Send does not take `re`. Each message row has id `msg-<seq>`. A message with `re` shows it in the message foot as a link to `/conversations/{name}?before=<re+1>#msg-<re>`, which opens that conversation with the referenced message at the top of the group, including a message older than the newest 50. A conversation named `.` or `..` shows `re` as text. A transcript served with `before` is a history view. Its top links to the newest group, which is the live view. A message body is rendered as Markdown. The stored text stays in the message. Markdown shows that text, and Copy writes it. An empty transaction id is filled in the page when Send is submitted. The server does not invent one and does not keep the place in the transcript or the id. A stored send redirects to the conversation, which clears the field. Any other result leaves the form open with the posted id. The page does not create, wait, close, or manage members. `GET /events` is a Server-Sent Events stream for one view. With no view parameter it follows Messages, `conversation=<name>` follows that transcript, `view=list` follows Conversations, and `conversation=<name>&view=history` follows a history view. It starts after query `after=<seq>` or the `Last-Event-ID` header. When both are present, the header wins. `view=list` takes neither. A history stream calls `/watch` with no `cursor`, sends `conversations` and `meta`, and never sends `message` or `reset`. It ignores `Last-Event-ID`, and `after` is answered `400`. Each stream is its own client of the bus and calls `/watch`, not `/wait`. It sends `message` with `id: <seq>` for each message of its view, `conversations` with the Open and Closed sections and the search index on every view, and, on a transcript, `meta` with the side panel at stream start and when it changes. A view that missed more than 50 of its messages gets `reset`, and the stream ends. A quiet stream sends a comment every 25s. A malformed position or view, `view=list` with a conversation, `view=history` without a conversation or with `after`, and a conversation name the bus refuses are answered `400` with a plain-text reason. A bus that is away ends a `200` stream, so the browser reconnects. Event data is HTML from the same template blocks as the pages. The stream position comes from the tab and is not stored. Each visible tab holds one stream for its view and updates in place, except that a history view shows no new message. A new message appears at the top of Messages or its transcript with a brief highlight, and nothing is trimmed. Conversations, the search index, and the side panel follow the list. The open Send form, Markdown toggles, and the search box are kept. A hidden tab closes its stream and catches up from its last seq when it is visible again. On `reset` the tab reloads the newest group of its view, without `before`, and opens a new stream from it. A failed reload is retried after 2s, doubling to 30s, while the tab is visible. The stream seq lives only in the tab's script and is not shown or stored.

```bash
hotseat web --listen 127.0.0.1:4808
hotseat web --address 127.0.0.1:4727 --listen 127.0.0.1:4808
hotseat web --address 192.0.2.10:4727 --listen 127.0.0.1:4808 --token-file /run/hotseat/token
```

Build with `CGO_ENABLED=0 go build -o hotseat ./cmd/hotseat`.
